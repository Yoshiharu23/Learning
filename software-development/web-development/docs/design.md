# 構成と設計の学習メモ

## 公開用に作り直した範囲

実際のWeb開発で学んだ内容から、画面・API・入力検証・テストを抜き出し、架空のタスク管理アプリとして再実装しました。元のリポジトリの履歴、サービス名、具体的な用途、利用者・組織の情報、画面画像、接続先、環境設定は掲載していません。

公開サンプルには外部認証・DB・外部API・配置用設定を含めず、主な実行時依存をNext.js・React・React DOMに絞りました。学習内容の全機能を再現するものではなく、短いコードで処理の流れを追うための構成です。

## サンプルの処理の流れ

```text
画面（React）
  └─ fetch /api/tasks
       └─ Route Handler（HTTPの受付と応答）
            ├─ 入力検証（unknown → 検証済みの型）
            └─ 保存処理（サーバープロセス内のメモリ）
```

| 場所 | 責務 | 確認する点 |
| --- | --- | --- |
| `src/components/task-board.tsx` | 入力、一覧、通信状態、検索結果の表示 | 通信失敗時に入力を保持する、操作中の重複送信を防ぐ |
| `src/app/api/tasks/route.ts` | HTTPメソッド、JSON解析、ステータスコード | 不正なJSON・入力は400、存在しないIDは404 |
| `src/lib/tasks.ts` | タスクの型、入力検証、検索 | 空白・文字数・不明な状態値、複数条件の組み合わせ |
| `src/lib/store.ts` | 初期データとCRUD | IDの発行はサーバー側、保存の仕組みをUIから分離 |
| `tests/` | 単体テストとE2Eテスト | 入力境界と、画面からAPIを通る一連の操作 |

## API

| メソッド | リクエスト | 正常時 | エラー時 |
| --- | --- | --- | --- |
| GET `/api/tasks` | なし | 200：`{ tasks }` | — |
| POST `/api/tasks` | `{ title, description, status }` | 201：`{ task }` | 400：JSON・入力が不正 |
| PATCH `/api/tasks` | `{ id, title, description, status }` | 200：`{ task }` | 400：入力が不正、404：IDが存在しない |
| DELETE `/api/tasks` | `{ id }` | 200：`{ deleted: true }` | 400：IDが不正、404：IDが存在しない |

タイトルは前後の空白を除いて1〜80文字、説明は0〜300文字、状態は`todo`または`done`です。サーバーで検証し、Reactでは文字列として描画します。任意のHTMLは扱いません。

## 実際の開発から学んだ設計

### 認証と認可を分ける

認証は誰が操作しているかを確かめ、認可はその人に対象データの操作を許すか判断します。ボタンの表示制御だけではAPIへの直接アクセスを防げません。実際の開発では、サーバーでの権限判定と、PostgreSQLのRLSによる行単位の制御を組み合わせる構成を学びました。

公開サンプルにはこの仕組みはありません。認証・認可付きのアプリへ拡張するなら、APIで検証した利用者をもとに対象データの権限を判定し、DBにもその条件を反映します。

### データの検証を境界に置く

ブラウザ側の入力制約は操作を助けますが、APIを直接呼ぶ場合にも同じルールが必要です。そのため、サンプルではUIから独立した関数で検証し、不正な値を保存処理へ渡さないようにしています。

### 永続化には別の責務がある

メモリ保存は流れの説明に向いていますが、再起動後の保持、同時更新、複数サーバーでの整合性を扱えません。DBへ移す場合は、列の制約、更新権限、競合時の扱い、マイグレーションと復旧手順も設計する必要があります。

### 確認方法を複数用意する

型検査は型の不整合、単体テストは入力とデータ処理、E2Eテストは画面とAPIの接続を確認します。実際の開発ではこれらをCIへ組み込み、PRで変更内容と検証結果を共有する進め方を学びました。このサンプルでは各検証をローカルコマンドで再現できます。
